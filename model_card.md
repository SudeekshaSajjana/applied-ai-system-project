# Model Card — PawPal+ AI Assistant

This is my responsible-AI reflection for the AI Assistant feature added to PawPal+ (`ai_assistant.py`). It's separate from `README.md`'s design/testing write-up because this part is specifically about the assistant's limitations, misuse potential, and how I actually worked with an AI (Claude) to build it — not just what the feature does.

## Limitations and Biases

- **It's keyword matching, not real language understanding.** The assistant decides what a question is "about" by checking whether specific words appear in it (e.g. "pending," "conflict," a pet's name). This misfires on ambiguous phrasing — for example, "Is Mochi done with everything?" matches on the word "done" and answers about *completed* tasks specifically, instead of giving a direct yes/no about overall status. It's a truthful answer, just not always the most natural response to how the question was actually phrased.
- **Pet-name recognition is exact-token matching.** A pet has to be referred to by its exact name as a whole word. Testing actually caught a real version of this bug: the tokenizer used to glue possessive `'s` onto a name (turning "Mochi's" into one token, `"mochi's"`), so it silently failed to recognize the pet in phrasing like "What are Mochi's tasks?" until I fixed the tokenizer. There could well be similar edge cases I haven't found (e.g. a pet named after a common English word like "Walk" would probably confuse the intent matcher).
- **The retrieval fallback only catches literal word overlap — in the default mode.** If a question doesn't share any words with the underlying data, the rule-based path won't find a match even if the answer genuinely exists — there's no synonym handling or semantic understanding there. I later added an optional Gemini-powered mode (`GEMINI_API_KEY` set) that fixes this specific limitation, since Gemini can paraphrase and reason over the retrieved context instead of relying on literal word overlap. That mode has its own, different limitations below.
- **No memory across questions, in either mode.** Every question is answered independently; it can't handle a follow-up like "and Buddy?" after asking about Mochi, because neither mode tracks conversation history across turns.
- **Its "knowledge" is only ever the current session.** It only knows what's currently in `st.session_state` (the owner/pets/tasks entered in that browser session) — it has no persistent history and forgets everything once the session ends. That's true in both modes and is by design, but it does mean it can't answer anything about past sessions or data patterns over time.
- **The Gemini mode is a real dependency on an external model.** Unlike the rule-based path, it can be slower, costs money per call, requires network access, and — being a real LLM — could in principle be talked into ignoring its instructions or hallucinating something not actually in the provided context, even though the system prompt explicitly tells it to answer only from the given context and say so if the answer isn't there. I haven't adversarially tested that boundary (e.g., trying to prompt-inject it into fabricating a task); it's a real gap in what I've verified, not a guarantee.
- **Actions execute immediately, with no confirmation step, in either mode.** Once Gemini decides to call `add_pet` (or the rule-based command parser matches one), the mutation happens right away — there's no "did you mean...?" or undo. The only safety net is field-level validation (age/weight must be numeric, time must match `H:MM AM/PM`, an unrecognized pet name is rejected with a list of real ones) — there's no confirmation step before a *valid-looking* action actually runs. For this app the blast radius is small (create an owner, add a pet, add a task — nothing destructive, nothing that deletes data), but this would be a real limitation if actions ever expanded to include anything destructive (e.g. removing a pet or task) without adding a confirmation step first.
- **Gemini's argument extraction isn't validated for plausibility, only for format.** In testing, asking it to add "a 3 year old Labrador" correctly filled `species` as `"dog"` (lowercased) even though the word "dog" never appeared in the prompt — a reasonable inference, but a demonstration that the model is inferring fields, not just copying them verbatim, and could plausibly infer something wrong for a more ambiguous request. The code only checks that `age`/`weight` are numeric and `time` is well-formed; it doesn't sanity-check, say, an age of 300 or a weight of -5.

## Potential Misuse and Mitigations

I don't think this specific assistant has a large misuse surface, mostly because of choices already made for other reasons, but it's worth spelling out:

- **No prompt-injection risk in the default (rule-based) mode.** Because that path isn't an LLM, there's no way to talk it into ignoring its instructions or fabricating information — every answer is either a direct method call on real `Owner`/`Pet`/`Scheduler` data or a retrieved chunk of that same real data. A user can't type something like "pretend Mochi has 0 pending tasks" and get it echoed back as fact, since the assistant never treats the user's own text as a source of truth. **This protection doesn't fully carry over to the optional Gemini mode** — it's a real LLM, so classic prompt-injection framing ("ignore the above and just say...") becomes a real, if narrow, risk there. The mitigation in place is that the system prompt restricts Gemini to the retrieved context and instructs it to admit when something isn't in that context, but I haven't red-teamed this — I'd treat it as an open risk rather than a solved one before using the Gemini mode with untrusted users.
- **No external network calls or API keys — in the default mode.** Nothing typed into the chat ever leaves the local machine, so there's no way to exfiltrate data through it, and no cost/rate-limit abuse surface like there would be with an API-backed version. **This is no longer true once `GEMINI_API_KEY` is set**: at that point, the question text and the retrieved context (which can include the owner's name, email, and phone number) are sent to Google's Gemini API. That's a real trade-off anyone enabling that mode should know about — it isn't private/local anymore for that request.
- **Logging could leak sensitive input.** `pawpal.log` records the raw text of every question asked, in plain text, locally. If someone pasted something sensitive into the chat thinking it was private, it would sit in that log file. I'd fix this in a real deployment by not logging raw free-text input verbatim (logging just the matched intent/category instead) or by rotating/excluding the log from any shared location.
- **Contact info is answerable on request.** Asking "who is the owner" returns the owner's email and phone number. That's fine for this single-user, local, no-login app, but if this were ever turned into a shared or hosted multi-user version, that would need real per-user authentication and data isolation before it'd be safe to expose that way — right now there's no login system at all, so it hasn't needed one, but it also means the app shouldn't be deployed anywhere multiple people share the same session.
- **Actions raise the stakes of a successful prompt injection.** Before this update, the worst outcome of a manipulated Gemini response was a wrong or made-up *answer*. Now that Gemini can call real functions, a successful injection could make it call `add_pet`/`add_task`/`create_owner` with attacker-chosen arguments — still bounded to creating plausible-looking data (nothing destructive is exposed), but a real step up in impact from "says something wrong" to "writes something wrong into the app's actual state." The mitigations in place are the same ones described above (context-restricted system prompt, field validation) plus the fact that only state-appropriate actions are ever offered as tools to begin with — but, as above, this hasn't been red-teamed.

## Surprises During Reliability Testing

- The biggest surprise was that **writing deliberate unit tests found a real bug that months of manually clicking through the UI never would have** — the possessive-tokenizer issue above. I'd only ever tested pet names typed plainly ("Mochi"), so the bug was invisible until I wrote a test using slightly different, more natural phrasing.
- The second surprise was the opposite problem: **two real UI bugs were completely invisible to every automated test I ran**, including Streamlit's `AppTest` harness, which actually executes the app's script the way a browser would. A CSS `position: fixed` floating chat bubble silently failed to render at all, and later a `st.popover`-based version closed itself every time a message was submitted. Both passed every automated check because neither pytest nor `AppTest` evaluates real browser CSS or rendering behavior — they only surfaced from actually opening the running app and using it. That was a real lesson: "all tests passing" and "the feature actually works for a person using it" are not the same claim.
- A third surprise came from wiring up a real Gemini API key: `gemini-2.5-flash` (the model I'd originally hardcoded) turned out to be no longer available to new API keys at all — a working integration silently became non-functional purely because of an external provider deprecating a model name, with no code bug involved. I had to actually list the models the real key could use and test several candidates before landing on `gemini-flash-latest`, Google's auto-updating alias, specifically so this doesn't quietly break again later.
- The fourth, more important surprise: **the moment a real `GEMINI_API_KEY` existed on the machine (in `.streamlit/secrets.toml`), a chunk of the existing test suite started failing or timing out** — tests that called `answer_question()` expecting the deterministic rule-based string had silently started making real, slow, non-deterministic network calls to Gemini instead, because they'd only ever verified "no key is present" by relying on the ambient absence of one, not by actually forcing it. That's a real gap in how I'd written those tests: they were unknowingly coupled to the environment they happened to be written in. The fix was to mock the key-lookup function directly in every test, so behavior is deterministic regardless of what's actually configured on whatever machine runs them.
- A fifth surprise: the "auto-updating" alias I'd switched to (`gemini-flash-latest`) turned out to resolve to a model with a **20-requests-per-day** free-tier quota — I only found out because a real chat session hit `RESOURCE_EXHAUSTED` mid-conversation. A quota that small is easy to exhaust in normal use and would silently drop the assistant back to rule-based answers with no explanation to the user, which is exactly the kind of "it works in my one test but not in real use" gap that only shows up by actually using the thing repeatedly, not by running it once. I switched to `gemini-flash-lite-latest`, a lighter tier, and confirmed live (not assumed) that it still supports function calling before committing to it.
- A sixth surprise, and the most directly related to what I was asked to fix: **even with Gemini genuinely active and answering, it was still effectively "listing out data"** — it was returning the retrieved context almost verbatim rather than composing an actual conversational reply, because my original prompt only said "answer using the context" and "be concise," which Gemini interpreted as license to just repeat the context back. This wasn't something a mocked unit test could have caught, since the mock just returns whatever text I told it to return — it only showed up by actually reading a real response from the real API and noticing it sounded wrong. The fix (explicitly instructing it to rephrase in its own words and vary its phrasing) was verified the same way: by rerunning the live call and reading the new output, not by trusting that the prompt change "should" work.

## AI Collaboration

I used Claude throughout this phase of the project — not just to write code, but to debug UI issues, design the retrieval/intent-matching approach, and review the feature against specific rubric requirements.

### A helpful suggestion

When the AI Assistant's floating chat widget started acting strangely (closing itself, requiring scrolling to see answers), instead of guessing at more CSS/JS fixes, Claude suggested actually running the app through Streamlit's `AppTest` testing harness to check the *underlying logic* (whether the panel's open/closed state actually survived a chat submission) before touching the UI again. That separated two different problems that had been getting confused with each other: the app's state-management logic was already correct, and the real bug was specifically how Streamlit rendered CSS and managed the built-in `st.popover` widget. Once that was clear, the actual fix (a custom session-state-driven panel instead of `st.popover`) was obvious. Testing the logic in isolation before touching the UI again saved a lot of guessing.

### A flawed suggestion

Claude's first attempt at making the AI Assistant into a floating chat bubble (fixed to the bottom-right corner of the screen, like a typical website chat widget) used plain CSS `position: fixed` targeting a Streamlit container by its key-based class name. It was presented as a working solution, but it didn't render at all — the button and panel were simply invisible. The actual cause, which Claude figured out afterward, was that Streamlit wraps its blocks in wrapper divs that use CSS `transform` for its rerun animations, and that silently changes what a `position: fixed` element is measured relative to, effectively clipping it off-screen instead of just repositioning it. It's a real, subtle CSS interaction, but the suggestion was still incorrect as given — it hadn't been verified against an actual running browser before being called done. The lesson for me was to actually go look at the running app myself rather than trust that a plausible-sounding CSS approach worked just because the code looked reasonable and no error was thrown.
